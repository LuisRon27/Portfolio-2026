1. TÍTULO PROFESIONAL
────────────────────────────────────────────────────────────────────────────────
Sistema de Gestión de Reservas para Auditorio Corporativo
(Reserva Auditorio HM)

2. SUBTÍTULO
────────────────────────────────────────────────────────────────────────────────
Aplicación web full-stack para la administración de reservas de auditorio con
calendario interactivo, detección de conflictos horarios, reservas batch,
notificaciones por email y control de acceso por roles.

3. DESCRIPCIÓN CORTA
────────────────────────────────────────────────────────────────────────────────
Sistema web interno desarrollado para el Grupo Oncomed Reno / Henry Moore que
permite a los empleados reservar el auditorio corporativo de forma eficiente.
Incluye calendario visual (FullCalendar), creación de reservas individuales o
múltiples (batch), verificación automática de conflictos horarios, notificaciones
por correo electrónico, autorización jerárquica y recursos opcionales
(videoconferencia, proyector). Construido con PHP, SQL Server, Bootstrap 5,
JavaScript vanilla y jQuery.

4. DESCRIPCIÓN TÉCNICA
────────────────────────────────────────────────────────────────────────────────
Arquitectura monolítica clásica con PHP del lado del servidor (sin framework)
implementando un patrón de capas básico: Capa de presentación (HTML+CSS+JS),
Capa de lógica de negocio (Clases PHP orientadas a objetos), Capa de datos
(SQL Server vía sqlsrv), y endpoints AJAX tipo REST-like para operaciones
CRUD asíncronas. El frontend utiliza Bootstrap 5.2.3 con personalización de
paleta de colores corporativa (#685783 / #d9ad27), FullCalendar 6.1.10 como
componente principal de agenda visual, y JavaScript vanilla con fetch() para
comunicación asíncrona. La autenticación es mediante sesiones PHP con
verificación contra tabla corporativa de usuarios (SQL Server existente) más
validación de acceso granular por aplicación. El módulo de email utiliza
PHPMailer con SMTP autenticado. La base de datos es Microsoft SQL Server 201x
en servidor de red interno (192.168.0.224). Sin framework PHP, sin ORM,
sin sistema de plantillas, sin npm/webpack — depende exclusivamente de
librerías CDN y bundles manuales.

5. STORYTELLING (CASO DE USO REAL)
────────────────────────────────────────────────────────────────────────────────
Contexto: El Grupo Oncomed Reno / Henry Moore es una empresa de salud con
múltiples sedes y un auditorio corporativo compartido. Anteriormente, la
reserva del auditorio se gestionaba de forma informal (mail, voz a voz,
planillas Excel compartidas), generando conflictos de horario, dobles reservas
y falta de trazabilidad.

Solución: Se desarrolló una aplicación web interna que se integra al ecosistema
digital existente de la compañía (portal corporativo, base de usuarios activa
en SQL Server, servidor SMTP propio). El sistema permite a cualquier empleado
con acceso ver el calendario en tiempo real, crear reservas puntuales o
recurrentes en múltiples fechas, recibir confirmación por email, y a los
autorizantes designados supervisar las reservas. La UI está diseñada con la
identidad visual corporativa (violeta/dorado) y es responsive.

Resultado: Eliminación completa de conflictos de agenda no detectados,
trazabilidad total de quién reserva qué y cuándo, notificación automática a
partes interesadas (sistemas@hmoore.com.ar, administración), y empowerment
de los empleados para autogestionar sus reservas sin intermediarios.

────────────────────────────────────────────────────────────────────────────────
Lenguajes:

  - JavaScript ES5/ES6 (vanilla, sin framework frontend)
  - HTML5, CSS3

Backend:

  - Patrón de clases: ClaseAuth, ClaseLogin, ClaseReservas, ClaseEmail
  - Sesiones PHP para estado de autenticación

Base de Datos:
  - Microsoft SQL Server (ruta: 192.168.0.224, base: Hmoore)

  - SMTP: 149.50.128.101:587, TLS, autenticación básica

Infraestructura:
  - Servidor Web: Apache/XAMPP (inferido por la ruta \xampp\htdocs\)
  - Servidor BD: SQL Server en red interna (192.168.0.224)

  - Sin Docker, sin CI/CD, sin cloud (entorno on-premise corporativo)

Flujo de navegación:
  1. index.php → verifica sesión activa → redirige a login o al calendario
  2. Login → POST a clase_login_acceso.php → autentica contra SQL Server →
     verifica acceso a la aplicación (UsuariosAplicaciones) → crea sesión →
     redirige a Pages/Reservas/index.php
  3. Calendario → FullCalendar carga eventos vía API (GET obtener_reservas.php)
  4. Click en fecha → modal "Nueva Reserva" → formulario con fecha, hora,
     título, motivo, responsable, recursos
  5. "Ver Preview" → verifica conflicto para CADA fecha (Promise.all + fetch)
  6. "Guardar" → si es simple → crea_individual; si batch → crea_batch
     → notificación por email → recarga calendario
  7. Click en evento existente → modal detalle → botón Editar/Eliminar
     (solo visible para el propietario)

Patrón: Front Controller simplificado (index.php como gateway) + Page Controller
         (cada página se sirve a sí misma) + API endpoints tipo RPC.

9. AUTENTICACIÓN Y ROLES
────────────────────────────────────────────────────────────────────────────────
Mecanismo:
  - Sesiones PHP nativas (session_start(), $_SESSION)
  - Login con usuario y contraseña contra tabla Usuarios (pass en texto plano)
  - Verificación de acceso por aplicación (tabla UsuariosAplicaciones con
    campo TipoUsuario)
  - Sin password hashing (pass en texto plano — riesgo de seguridad, aunque
    es red interna corporativa)
  - Sin 2FA, sin JWT, sin OAuth

Roles:
  - TipoUsuario se almacena en sesión desde UsuariosAplicaciones
  - Ownership: solo el IDUsuario creador puede editar/eliminar su reserva
    (verificado en procesar_reserva.php con esPropietario())
  - Visualización: todos los usuarios autenticados ven todas las reservas
  - Autorizantes: lista hardcodeada en select HTML (7 personas: directores,
    jefes de área)

13. SEGURIDAD
────────────────────────────────────────────────────────────────────────────────
Fortalezas detectadas:
  - htmlspecialchars() en salida de datos (previene XSS)
  - Verificación de autenticación en cada API endpoint
  - Verificación de ownership antes de editar/eliminar
  - Redirección forzada si no hay sesión
  - Parámetros preparados (prepared statements) en todas las consultas SQL
    (vía sqlsrv_query con parámetros separados, evitando SQL injection)
  - Session regen implícita (no explícita, pero se usa sesión única)
  - min en input date (no permite fechas pasadas en frontend)

Debilidades / Observaciones:
  - Passwords en texto plano en BD (no hay hash: ni bcrypt, ni MD5, ni SHA)
  - Sin HTTPS (red local, pero igual riesgoso)
  - Sin CSRF tokens en formularios
  - Sin rate limiting en login
  - Sin logs de intentos fallidos de login
  - SMTP credentials hardcodeadas en ClaseEmail.php
  - Conexión a BD con credenciales en texto plano en Conexion.php
  - Sin validación del lado del servidor para fechas pasadas (solo frontend)
  - Estado de sesión sin regeneración periódica
  - Sin protección contra session fixation (no se regenera session_id tras login)
  - Error reporting expuesto (sqlsrv_errors()) en entorno de producción

14. PERFORMANCE
────────────────────────────────────────────────────────────────────────────────
Puntos a favor:
  - Llamadas asíncronas (fetch) sin recarga de página
  - CDN para librerías estáticas (caché del navegador)
  - Carga inicial de eventos completa (no paginada, pero volumen esperado bajo)
  - Sin frameworks pesados del lado del servidor
  - Sin ORM (consultas directas, mínimo overhead)

Puntos de mejora:
  - Sin caché de consultas (cada GET a obtener_reservas.php ejecuta SELECT)
  - Sin lazy loading para eventos (para volumen alto, recomendar paginación
    por rango de fechas)
  - Sin índices en Fecha, HoraInicio, HoraFin
  - Carga del calendario completo recarga la página (location.reload())
  - Single punto de entrada — sin separación de assets crítica

20. COMPLEJIDAD Y SENIORITY DEMOSTRADOS
────────────────────────────────────────────────────────────────────────────────
Nivel: Junior-Mid (SSR trainee a SSR inicial)
         con momentos de seniority en frontend.

Fundamentos de la evaluación:
  - Arquitectura: Monolítica simple, sin framework. Buena para un proyecto
    interno de alcance limitado, pero no escala a equipos grandes.
  - Backend: PHP OOP básico pero correcto. Falta de type hinting,
    excepciones, y estándares modernos (PSR, Composer) indican un dev que
    aprendió PHP "en la práctica" más que con formación formal moderna.
  - Frontend: Notablemente más trabajado que el backend. El calendario.js
    tiene 674 líneas bien estructuradas con funciones modulares, uso de
    Promises (Promise.all), fetch(), manipulación dinámica del DOM,
    eventos, y manejo de estado. Esto muestra un skill más fuerte en
    frontend vanilla.
  - CSS: Muy trabajado (541 líneas de reservas.css con variables CSS,
    animaciones, gradients, sombras, transiciones, responsive completo).
    Demuestra atención al detalle visual y experiencia con diseño UI/UX.
  - BD: Modelado correcto pero sin índices adicionales, sin FKs explícitas,
    sin considerar normalización. Conocimiento básico intermedio.
  - Seguridad: Conceptos básicos implementados (prepared statements,
    htmlspecialchars) pero faltan estándares profesionales (password hash,
    CSRF, HTTPS, secrets management).
  - DevOps: Nulo (sin CI/CD, sin Docker, sin cloud — esperable para
    proyecto interno corporativo on-premise).
  - Testing: Ausente.

Conclusión de seniority:
  Desarrollador full-stack con perfil predominantemente frontend,
  aproximadamente 1-3 años de experiencia laboral, con sólida base en
  HTML/CSS/JS y conocimientos operativos de PHP + SQL Server.
  Capaz de entregar un producto funcional, bien diseñado visualmente, y
  con buenas prácticas de seguridad básicas. Le falta incorporar
  estándares modernos de PHP, testing, y DevOps para considerarse SSR.
