────────────────────────────────────────────────────────────────────────────────
4. DESCRIPCIÓN TÉCNICA (200 palabras)
────────────────────────────────────────────────────────────────────────────────

Sistema completo de gestión de agenda médica desarrollado para la entidad de
salud William Osler. El backend es una API RESTful en ASP.NET Core 10 con
Entity Framework Core 10, SQL Server, autenticación JWT con políticas de
autorización por claims (MedicoAgenda, SecretariaAgenda, SistemaAgenda), 31
tablas normalizadas, 20 controladores con más de 50 endpoints, middleware de
logging y manejo global de excepciones, generación de reportes PDF con QuestPDF,
y Serilog para auditoría estructurada.

El frontend es una SPA en React 19 + TypeScript 5.9 con Vite 7, arquitectura
Feature-Sliced Design, estado global con Zustand + TanStack Query para datos
de servidor, formularios con react-hook-form + Zod, 24 componentes shadcn/ui
con Tailwind CSS 4, y enrutamiento con React Router 7 (HashRouter).

Incluye: gestión completa de turnos (creación, edición, bloqueo, anulación,
llegada/ingreso/salida), administración de pacientes con búsqueda avanzada y
múltiples coberturas médicas, catálogos dinámicos (profesionales, especialidades,
entidades, diagnósticos OMS, consultorios), panel de agenda diaria con filtros
múltiples y paginación server-side, reportes PDF descargables, y auditoría de
cambios con log de pacientes y turnos.

Arquitectura on-premise desplegada en infraestructura propia, con versionado
semántico, control de concurrencia optimista (RowVersion), branch strategy
Git Flow (master/develop/features), y preparada para CI/CD en GitHub Actions.

────────────────────────────────────────────────────────────────────────────────
5. STORYTELLING — CONTEXTO REAL
────────────────────────────────────────────────────────────────────────────────

William Osler es una institución de salud con múltiples profesionales,
especialidades y consultorios que necesitaba modernizar su sistema de gestión
de turnos. El sistema anterior carecía de una interfaz web moderna, no permitía
la gestión en tiempo real desde cualquier dispositivo, y los reportes se
generaban manualmente.

El objetivo fue construir desde cero una plataforma completa que reemplazara
el sistema legacy, con foco en: usabilidad para administrativos y médicos,
gestión eficiente de la agenda diaria, trazabilidad completa de cada turno
(desde la creación hasta la atención), y reportes automatizados.

El proyecto se desarrolló siguiendo una branch strategy Git Flow con features
paralelos (agenda-día, fichas de paciente, gestión de turnos, administración
de médicos), integración progresiva en develop y despliegue a producción desde
master. Actualmente se encuentra en etapa avanzada de desarrollo con
funcionalidades core completas y en uso real.

9. AUTENTICACIÓN Y AUTORIZACIÓN
────────────────────────────────────────────────────────────────────────────────

  • Tipo: JWT (JSON Web Token) con HMAC-SHA256
  • Emisor: ApiAgenda | Audiencia: ApiAgendaUsers
  • Expiración: 30 días
  • Claims principal: sub (IDUsuario), nombre, email, role (CatLaboral),
    tipoUsuario, más claims permiso individuales por aplicación
  • Políticas de autorización:
      - MedicoAgenda   → claim permiso = "Medico Agenda"
      - SecretariaAgenda → claim permiso = "Secretaria Agenda"
      - SistemaAgenda  → claim permiso = "Sistema Agenda"
      - AgendaAccess   → OR de las tres anteriores (compuesta)
  • Endpoints públicos solo: /api/auth/login y /api/version
  • Todos los demás endpoints requieren [Authorize(Policy = "AgendaAccess")]
  • Frontend: token almacenado en cookie, interceptor axios añade header
    automáticamente, verificación de versión API en cada respuesta

  NOTA: Las contraseñas se almacenan en texto plano (limitación detectada).
  Inferencia: proyecto en desarrollo, pendiente migración a hash (bcrypt).

18. SEGURIDAD
────────────────────────────────────────────────────────────────────────────────

  ✅ FORTALEZAS DETECTADAS
  • JWT con HMAC-SHA256 + claims personalizados
  • Autorización basada en políticas (no solo roles)
  • Middleware de excepción: no filtra stack traces ni datos sensibles
  • RowVersion para control de concurrencia optimista
  • Auditoría completa de cambios (log de pacientes y turnos)
  • CORS configurable (actualmente AllowAnyOrigin — entorno desarrollo)
  • HTTPS redirection habilitado
