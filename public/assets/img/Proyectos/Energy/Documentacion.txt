Energy Square es un CMS inmobiliario desarrollado íntegramente en PHP vanilla
(procedural) con MySQL como motor de base de datos. Consta de 34 archivos fuente
(~6.500 líneas de código) distribuidos en frontend público y backend
administrativo. La base de datos relacional incluye 7 tablas normalizadas:
usuarios, proyectos, propiedades, servicios, ambientes, comodidades e imágenes.

El frontend utiliza Bootstrap 5.3.3, CSS vanilla (376 líneas con variables
custom y diseño responsive), JavaScript nativo para filtrado en tabla y
notificaciones. Las fuentes son Montserrat (Google Fonts) e iconos de
Font Awesome 6 y Bootstrap Icons. Se integra Google Maps Embed API para
geolocalización de propiedades.

El backend implementa autenticación por sesión con bcrypt (password_hash/
password_verify), CRUD completo en 5 módulos, paginación server-side,
subida de archivos con naming uniqid(), eliminación en cascada multi-tabla
con transacciones MySQL, y guards de sesión con headers PSR-style.

Todo el stack corre sobre infraestructura LAMP/LEMP tradicional sin
frameworks, sin ORM, sin bundlers, sin dependencias npm/composer.
Las dependencias frontend se sirven vía CDN. Incluye seed data SQL y
schema completo listo para deployment.

5. STORYTELLING — CONTEXTO Y VISIÓN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Vaca Muerta, Neuquén, es la reserva de shale oil y shale gas más importante
de Argentina y una de las más grandes del mundo. La fiebre energética ha
generado una explosión demográfica y de demanda inmobiliaria en localidades
como Añelo, convirtiendo el mercado de propiedades en un sector crítico pero
desatendido digitalmente.

Energy Square nace para cubrir ese gap: una inmobiliaria especializada que
necesitaba una plataforma digital profesional para exhibir proyectos en
desarrollo (como Black Point), captar leads calificados, y gestionar
internamente el catálogo de propiedades con todos sus atributos.

El proyecto fue desarrollado por un solo developer cubriendo frontend,
backend, base de datos, diseño visual, SEO, assets multimedia y deploy.
No es un proyecto académico ni un template: es un sistema en producción
diseñado para un negocio real con clientes reales.

El enfoque fue priorizar velocidad de desarrollo, simplicidad de hosting
(LAMP estándar, sin requisitos especiales) y funcionalidad completa sobre
arquitectura sobreingenierizada. Se eligió PHP vanilla justamente porque
permite deploy en cualquier hosting compartido sin depender de versiones
de frameworks o composer.

PATRÓN: LAMP tradicional sin framework (Flat-file routing)

index.php                              ← Entry point (ruteo manual)
  │
  ├── Config/
  │   ├── Conexion.php                 ← Singleton de conexión MySQLi
  │   └── Script.sql                   ← Schema + seed data
  │
  ├── Css/style.css                    ← Estilos globales
  ├── Js/Script.js                     ← JS global (filtros, notificaciones)
  ├── Images/                          ← Assets multimedia
  └── PDF/                             ← Brochures descargables

  └── Pages/
       ├── Admin/                      ← Zona privada (protegida por session)
       │   ├── Menu_Admin.php          ← Dashboard
       │   ├── Login/                  ← Módulo de autenticación
       │   ├── Usuarios/               ← CRUD usuarios
       │   ├── Proyecto/
       │       ├── Propiedad.php       ← Listado propiedades (admin)
       │       ├── Crud_Proyecto/      ← CRUD proyectos + archivos
       │       └── Crud_Propiedades/   ← CRUD propiedades multi-tabla
       │
       ├── Black Point/                ← Landing específica del proyecto
       ├── Blogs/                      ← Blog posts
       └── Propiedades/                ← Vista pública detalle propiedad

FLUJO DE DATOS:
  Browser → HTTP → index.php → MySQLi query → HTML render → Browser
  Admin → HTTP → Login.Validate.php → Session → Admin pages → CRUD → MySQL

MODELO DE DATOS (7 tablas normalizadas):
  users (1) ──────────────────── (sin FK, admin-only)
  proyectos (1) ──────────────── propiedades (N)
                                   ├── servicios (1:1)
                                   ├── ambientes (1:1)
                                   ├── comodidades (1:1)
                                   └── imagenes_propiedad (1:N)

TRANSACCIONES:
  Actualizar.Propiedad.php usa $conn->begin_transaction() y commit()
  para garantizar consistencia en updates multi-tabla.
  Eliminar.Proyecto.php implementa borrado en cascada manual:
    proyectos → propiedades → servicios → ambientes → comodidades → imágenes

PAGINACIÓN:
  Server-side con LIMIT/OFFSET + COUNT(*) paginación clásica (10 x página).

SUBIDA DE ARCHIVOS:
  - PDFs en /PDF/ con prefijo uniqid()
  - Fotos en /Images/ con prefijo uniqid()
  - Imágenes de propiedad en /Images/Proyectos/{nombre_proyecto}/
  - Limpieza de nombre de carpeta con regex (caracteres especiales eliminados)
  - Validación: solo client-side (accept attribute)

9. AUTENTICACIÓN Y SEGURIDAD
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

IMPLEMENTADO:
  ✔ Password hashing con password_hash(PASSWORD_DEFAULT) = bcrypt
  ✔ password_verify() en login
  ✔ Prepared statements en mayoría de queries (mysqli prepare/bind_param)
  ✔ Guard de sesión en páginas admin (Autenticacion.php incluido)
  ✔ Headers de seguridad: Cache-Control: no-store, no-cache, must-revalidate
  ✔ Botón de Logout con session_destroy()
  ✔ Estado activo/inactivo en usuarios (AND activo = 1 en login query)
  ✔ htmlspecialchars() en algunos outputs (parcial)

VULNERABILIDADES DETECTADAS (requieren corrección):
  ⚠ SQL Injection: Editar.Proyecto.php línea 32 — variable $id_proyecto
    directamente interpolada en WHERE sin prepared statement
  ⚠ SQL Injection: Editar.Propiedad.php línea 89 — $id_propiedad en WHERE
  ⚠ SQL Injection: Propiedad_Detalle.php líneas 27-85 — $id_proyecto y
    $id_propiedad en queries sin sanitizar
  ⚠ Path traversal potencial: Eliminar_Imagen.php línea 32 usa
    $_SERVER['DOCUMENT_ROOT'] concatenado con input del usuario
  ⚠ Credenciales hardcodeadas: Conexion.php almacena host/user/password
    en texto plano (actualmente placeholders vacíos)
  ⚠ Sin CSRF tokens en formularios admin
  ⚠ Validación de subida de archivos solo client-side (accept attribute),
    sin validación server-side de tipo MIME o extensión
  ⚠ DELETE vía GET en Eliminar.Usuario.php y Eliminar.Propiedad.php →
    vulnerable a CSRF y accidental deletion

NOTA PARA EL PORTAFOLIO:
  Las vulnerabilidades detectadas demuestran capacidad de auditoría de
  seguridad y conocimiento de OWASP Top 10. Mencionar que se identificaron
  y pueden ser corregidas como parte de una mejora planificada.

⚠ OPORTUNIDADES DE MEJORA (nivel senior):
─────────────────────────────────────────
  • Migrar a MVC (Laravel/Symfony) escalabilidad y mantenibilidad
  • Reemplazar todas las queries sin prepared statement por parámetros
  • Implementar validación server-side de tipos de archivo (MIME check)
  • Agregar CSRF tokens en todos los formularios
  • Cambiar DELETE GET por POST con confirmación
  • Usar .env para credenciales (no hardcode)
  • Implementar logging de actividades (quién, qué, cuándo)
  • Cache de queries con Redis o Memcached

  • Agregar Content Security Policy headers
  • Implementar HTTP-only cookies para sesiones
  • Agregar X-Frame-Options, X-Content-Type-Options headers
  • Validación server-side de todos los inputs (no solo client-side)
  • Implementar pruebas unitarias y de integración (PHPUnit)
  • Migrar a PDO (más moderno que mysqli, mejor manejo de errores)
  • Implementar API RESTful para desacoplar frontend/backend
  • Dockerizar la aplicación para entornos consistentes

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

DESAFÍO 1: Modelo de datos complejo para propiedades
  ─ Las propiedades tienen ~72 atributos distribuidos en 5 tablas
    (servicios, ambientes, comodidades, imágenes, datos principales).
  ─ SOLUCIÓN: Tablas 1:1 para cada categoría de atributos, con joins
    en las queries de lectura y transacciones en escritura.
  ─ IMPACTO: Datos normalizados sin redundancia, fácil de extender.

DESAFÍO 2: Gestión de archivos multimedia
  ─ Cada proyecto puede tener PDF, foto principal y múltiples imágenes.
  ─ SOLUCIÓN: Estructura de carpetas por proyecto, naming uniqid(),
    eliminación en cascada con limpieza de archivos del filesystem.
  ─ IMPACTO: Sin archivos huérfanos, escalable a miles de imágenes.

DESAFÍO 3: Sin framework ni ORM
  ─ Se decidió no usar Laravel/Symfony por simplicidad de hosting.
  ─ SOLUCIÓN: Arquitectura flat-file con includes manuales y queries
    mysqli con prepared statements.
  ─ IMPACTO: Cero dependencias, deploy en cualquier hosting PHP,
    pero código más verboso y sin autoloading.

DESAFÍO 4: SEO y contenido educativo
  ─ El público busca información sobre Vaca Muerta antes que propiedades.
  ─ SOLUCIÓN: Blog con contenido SEO optimizado, sección de datos
    de Vaca Muerta en landing, Open Graph tags.
  ─ IMPACTO: Posicionamiento orgánico para keywords del sector.

DESAFÍO 5: Proyecto para mercado específico
  ─ Nicho inmobiliario energético (Vaca Muerta) con poca competencia digital.
  ─ SOLUCIÓN: Landing dedicada "Black Point" con storytelling visual,
    video hero, galería, planos y llamado a la acción.
  ─ IMPACTO: Diferenciación en un mercado con poca presencia digital.
