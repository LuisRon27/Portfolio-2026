1. TÍTULO PROFESIONAL
--------------------------------------------------------------------------------
Sistema Web de Gestión de Documentación Técnica Interna (DMS)
"Manuales de Sistemas" — Portal Corporativo de Manuales TI


2. SUBTÍTULO
--------------------------------------------------------------------------------
Aplicación Web Full-Stack PHP + SQL Server para la administración centralizada
de manuales técnicos, procedimientos y documentación de infraestructura/sistemas
en un grupo de salud con múltiples sedes.


3. DESCRIPCIÓN CORTA
--------------------------------------------------------------------------------
Sistema web interno tipo DMS (Document Management System) que permite a un
departamento de Sistemas centralizar, organizar, buscar y mantener toda su
documentación técnica (manuales, instructivos, procedimientos) en un repositorio
digital con acceso web, categorización por áreas, filtros dinámicos y soft-delete.
Desarrollado en PHP nativo con SQL Server y Bootstrap 5, opera como módulo
dentro de un ecosistema corporativo más grande (portal intranet) del grupo de
salud Henry Moore / Oncomed Reno en Argentina.


4. DESCRIPCIÓN TÉCNICA
--------------------------------------------------------------------------------
Aplicación web full-stack construida con PHP procedural sobre Windows + XAMPP,
conectada a Microsoft SQL Server 2008+ mediante la extensión sqlsrv. Implementa
autenticación por sesión contra tabla de usuarios corporativa, CRUD completo de
documentos con carga de archivos (PDF, DOC, DOCX, XLS, XLSX), categorización
jerárquica (Áreas → Categorías → Documentos), paginación server-side + filtrado
client-side, búsqueda por texto libre y soft-delete lógico. La UI utiliza
Bootstrap 5.3 con modal CRUD, DataTables, Bootstrap Icons y estilos CSS
corporativos (violeta #685783 + amarillo #d9ad27). El manejo de archivos incluye
sanitización de nombres, validación de extensiones, peso en KB y organización
física por área en directorios separados. A nivel de seguridad usa consultas
parametrizadas (prepared statements) anti-SQLi y escape XSS con htmlspecialchars.


5. STORYTELLING / CONTEXTO DE NEGOCIO
--------------------------------------------------------------------------------
El departamento de Sistemas del grupo Henry Moore / Oncomed Reno (salud,
múltiples sedes en CABA) acumulaba años de documentación técnica dispersa en
carpetas de red compartidas, sin control de versiones, sin búsqueda y sin
categorización. Cada técnico o desarrollador guardaba manuales, instructivos y
procedimientos en su propia máquina o en directorios sin estructura. Esto
generaba pérdida de tiempo, duplicación de esfuerzos y riesgos operativos.

Se desarrolló "Manuales de Sistemas" como solución interna para centralizar
TODO el conocimiento del área: desde procedimientos de infraestructura (redes,
firewalls Fortigate, CCTV, telefonía VoIP) hasta manuales de desarrollo (SQL
Server, GtmApp, facturación, pads, bots, recetas digitales, etc.).

El sistema se integró como módulo del portal intranet existente, reutilizando
la autenticación corporativa. Hoy es la fuente única de verdad documental del
departamento, con más de 60 documentos técnicos cargados y accesibles desde
cualquier estación de trabajo interna sin necesidad de permisos de red.


6. FUNCIONALIDADES PRINCIPALES
--------------------------------------------------------------------------------
  a) Autenticación de usuarios contra base corporativa (login/logout con
     sesiones PHP).

  b) Landing page con tarjetas de Áreas activas del departamento (ej.
     "desarrollo", "infraestructura").

  c) Visualización de documentos por Área con tabla responsiva que muestra:
     título, categoría, descripción, icono de tipo de archivo, ruta de red
     (copiable al portapapeles), fecha de creación.

  d) Búsqueda en tiempo real por título/descripción (filtro client-side en JS
     sobre JSON embebido).

  e) Filtro dinámico por categoría (combinable con búsqueda).

  f) Paginación server-side (server) + client-side (JS) combinada: el listado
     server-side inicial de 10 registros se complementa con una copia JSON de
     todos los documentos para filtrado interactivo sin recarga.

  g) CRUD completo de documentos (manuales):
     - Crear: formulario modal con categoría, título, descripción + archivo
     - Editar: modificar metadatos y opcionalmente reemplazar archivo
     - Eliminar lógico (soft-delete): flag activo = 0, sin borrado físico

  h) CRUD completo de Categorías:
     - Asociadas a un Área
     - Modal unificado para crear/editar
     - Soft-delete (inactivación)

  i) Subida de archivos con:
     - Validación de extensiones (solo .pdf .doc .docx .xls .xlsx)
     - Sanitización de nombre (caracteres seguros + timestamp único)
     - Organización en subdirectorios por slug del área
     - Cálculo de peso en KB
     - Reemplazo controlado (elimina archivo anterior en edición)

  j) Soft-delete general: ningún DELETE FROM, solo UPDATE activo=0. El archivo
     físico NO se elimina al inactivar.

  k) Copia de ruta UNC de red al portapapeles ( \\server\share\ruta\archivo )
     para acceso directo desde Windows Explorer.

  l) Enlace a "documentación vieja" (legado HTML anterior al sistema).

  m) Navegación integrada al portal corporativo (volver, inicio, portal).

8. ARQUITECTURA DEL SISTEMA
--------------------------------------------------------------------------------
  Arquetipo: Aplicación Web Monolítica (PHP procedural)
  Patrón:    Page Controller (cada .php es una página-controladora)
  Modelo:    Sin framework MVC — PHP plano con separación de includes

  FLUJO DE SOLICITUD:

    Navegador
       │
       ▼
    Apache (XAMPP)
       │
       ▼
    index.php / area.php / categoria.php
       │
       ├── require("conexionSQL_Hmoore.php")   ← Conexión P/M a SQL Server
       ├── include("./includes/header.php")     ← Header corporativo
       ├── Lógica de negocio (consultas SQL)    ← Queries parametrizadas
       ├── HTML + PHP embebido (vistas)         ← Renderizado
       ├── include("./includes/footer.php")     ← Footer corporativo
       └── JS al final (Bootstrap + custom)     ← Interactividad

    CRUD:
      insert.manual.php / update.manual.php / delete.manual.php
      insert.categoria.php / update.categoria.php / delete.categoria.php
        → reciben POST/GET
        → validan
        → ejecutan SQL
        → redirigen (header Location)

  SEPARACIÓN LÓGICA:
    - /includes/        → Header y footer reutilizables
    - /crud/            → Operaciones de escritura (CUD)
    - /uploads/{area}/  → Archivos físicos organizados por área
    - index.php         → Vista principal (listado de áreas)
    - area.php          → Documentos por área (con todo el CRUD embebido)
    - categoria.php     → ABM de categorías

  DEPENDENCIA EXTERNA:
    - Conexión a BD compartida: ../../conexiones/conexionSQL_Hmoore.php
      (ruta relativa que sube dos niveles hasta la carpeta Sistemas/)

  RUTAS DE ARCHIVOS:
    - Los documentos se almacenan en uploads/{area_slug}/
    - El slug se obtiene limpiando el nombre del área (solo a-zA-Z0-9)
    - Cada archivo se renombra con timestamp_nombreoriginal para unicidad

    - ORDER BY para ordenamiento


10. AUTENTICACIÓN Y SEGURIDAD
--------------------------------------------------------------------------------
  MECANISMO DE AUTENTICACIÓN:
    - Login: formulario POST valida contra tabla Usuarios (IdUsuario + Pass)
    - Sesión: $_SESSION['username'] almacena el ID del usuario autenticado
    - Logout: session_destroy() + redirect a login
    - Tiempo de sesión: default PHP (hasta cierre de navegador o timeout)

  CONTROL DE ACCESO:
    - Sin roles/permisos explícitos: cualquier usuario autenticado tiene
      acceso completo a todas las operaciones CRUD
    - No hay verificación de sesión en cada página del módulo manuales
      (session_start() está pero no hay if(!isset($_SESSION['username'])))

  VULNERABILIDADES IDENTIFICADAS (para mejorar):
    ⚠ Contraseñas en texto plano (Pass sin hash) en la tabla Usuarios
    ⚠ Ausencia de CSRF tokens en formularios
    ⚠ Sin verificación de sesión en páginas del módulo (accesible sin login)
    ⚠ La extensión usada en delete.categoria.php referencia id_area pero no
       se recibe el parámetro en el código actual (roto? la URL no lo envía)

  FORTALEZAS DE SEGURIDAD:
    ✅ Prepared statements en TODAS las consultas (sqlsrv_query con parámetros)
       — protección total contra SQL Injection
    ✅ htmlspecialchars() en toda salida de datos — protección XSS
    ✅ Sanitización de nombres de archivo (preg_replace + basename)
    ✅ Whitelist de extensiones permitidas
    ✅ Validación de tipo POST en operaciones de escritura
    ✅ Type casting estricto ((int)$_POST['id'])

  SEGURIDAD EN ARCHIVOS:
    - Solo se permiten: pdf, doc, docx, xls, xlsx
    - El nombre final se construye con timestamp + nombre sanitizado
    - Los directorios se crean con permisos 0775/0777

14. PANEL ADMIN / CRUD
--------------------------------------------------------------------------------
  No existe un "panel admin" separado. La funcionalidad de administración está
  embebida en las vistas regulares:

  - Los botones de acción (editar/eliminar/agregar) son visibles para
    cualquier usuario autenticado.
  - No hay diferenciación entre usuario regular y administrador.
  - Las operaciones se realizan mediante modales Bootstrap que cargan
    formularios con action apuntando a los scripts CRUD.
  - Confirmación de borrado con confirm() nativo de JS.
  - La gestión de categorías tiene su propia página (categoria.php) que
    funciona como abm independiente.

18. PATRONES Y BUENAS PRÁCTICAS
--------------------------------------------------------------------------------
  ✅ IMPLEMENTADOS:
    - Consultas parametrizadas (prepared statements) en TODAS las queries
    - Escape de salida con htmlspecialchars()
    - Soft-delete lógico (no destrucción de datos)
    - Type casting (int) en inputs numéricos
    - Whitelist de extensiones (solo formatos seguros)
    - Sanitización de nombres de archivo (caracteres seguros + timestamp)
    - Separación de responsabilidades (vistas vs operaciones vs includes)
    - Redirección POST/GET después de operaciones de escritura (PRG)
    - Validación de método HTTP (POST check en operaciones de escritura)
    - Reutilización de componentes (header, footer)
    - Mensajes de error informativos (die con print_r de errores)
    - Responsive design con Bootstrap grid

  ⚠ NO IMPLEMENTADOS (OPORTUNIDADES DE MEJORA):
    - Autenticación faltante en páginas del módulo (sin check de sesión)
    - Contraseñas en texto plano (falta password_hash/password_verify)
    - Sin CSRF tokens
    - Sin validación server-side en algunos campos (descripción muy larga)
    - Sin logging de acciones (quién editó qué y cuándo)
    - Sin manejo de errores estructurado (die() genérico)
    - Sin sanitización de entrada GET en delete.categoria.php (parámetro
      id_area referenciado pero no recibido — posible bug)
    - Sin POO ni namespaces
    - Sin sistema de archivos con control de versiones
    - Sin caché ni optimización de assets
    - Código duplicado en la lógica de extensión/icono (server + client)


19. PERFORMANCE
--------------------------------------------------------------------------------
  PUNTOS FUERTES:
    - Paginación server-side (10 registros por página)
    - Búsqueda/filtro client-side sobre JSON precargado (sin recarga)
    - Assets vía CDN (Bootstrap, Icons) con caché del navegador
    - Consultas SQL con JOINs y filtros en WHERE

  PUNTOS DÉBILES:
    - La página area.php carga TODOS los documentos en un array PHP antes
      de paginar server-side, y también los embebe como JSON para el
      filtro client-side. Con 50+ documentos no hay problema, pero no escala
      a miles.
    - Sin lazy loading para nada
    - Sin compresión ni minificación de assets (todo es full-size CDN)
    - Sin índices explícitos (depende de la BD)
    - Las imágenes de fondo (foto.jpg) son pesadas para mobile

  ESCALABILIDAD:
    - Aceptable para 100-200 documentos y decenas de usuarios simultáneos
    - El cuello de botella sería la BD si el ecosistema completo (portal)
      comparte el mismo SQL Server
    - Para escalar a miles de documentos, habría que migrar a búsqueda
      server-side y paginación real

    Solución: Soft-delete en todas las entidades (activo=0 en lugar
    de DELETE). Los archivos físicos nunca se eliminan, solo se
    ocultan de la vista.

32. MÓDULO DE MONITOREO DE ERRORES EN TIEMPO REAL
================================================================================
   TÍTULO:  Sistema de Monitoreo de Errores Multi-Base de Datos
   RUTA:    /Sistemas/ManualesSistemas/Monitoreo/

   DESCRIPCIÓN GENERAL:
     Dashboard web en tiempo real que consolida y visualiza errores de
     aplicación desde dos bases de datos SQL Server independientes (Hmoore
     y AgendaWO). Proporciona cards de resumen por período, gráficos
     interactivos con Chart.js, tabla de errores con filtros combinados,
     detalle expandido en modal, y auto-refresh con notificaciones de
     nuevos errores sin recargar la página.

   FUNCIONALIDADES PRINCIPALES:
     a) Conexión simultánea a dos bases de datos (Hmoore + AgendaWO) desde
        un mismo dashboard, con lógica de consolidación de resultados.

     b) Cards de resumen con conteo de errores por período:
        - Últimas 24 horas (card primary)
        - Última semana (card warning)
        - Último mes (card danger)
        - Último año (card success)

     c) Gráfico de barras (Chart.js): Errores por aplicación en las
        últimas 24 horas, con datos agregados de ambas bases.

     d) Gráfico de línea (Chart.js): Tendencia de errores diaria en los
        últimos 7 días, también consolidado.

     e) Selector de base de datos: permite filtrar la vista por:
        - Ambas bases (default)
        - Solo Hmoore
        - Solo AgendaWO

     f) Tabla de errores en tiempo real con columnas:
        Fecha/Hora, Base Datos, Aplicación, Entorno (PROD/otros),
        Mensaje, Endpoint, Status Code, Usuario, IP, y botón de detalle.

     g) Filtros combinados:
        - Por período (24h, semana, mes, año)
        - Por aplicación (dropdown poblado dinámicamente)
        - Búsqueda por texto libre en mensaje/detalle/endpoint (con
          debounce de 500ms)

     h) Auto-refresh cada 30 segundos con contador regresivo visible,
        que actualiza la tabla, los contadores y detecta nuevos errores.

     i) Notificaciones de nuevos errores en tiempo real:
        - Alerta visual (banner rojo dismissible) con mensaje del error
        - Alerta sonora si el navegador lo soporta
        - Desaparece automáticamente a los 5 segundos

     j) Modal de detalle completo del error con:
        - Datos generales (BD, app, entorno, fecha, usuario, IP)
        - Endpoint, método HTTP, status code
        - Mensaje de error en alerta roja
        - Detalle técnico en preformateado con scroll
        - JSON Request formateado (pretty-print)

     k) Detección de errores nuevos mediante polling: consulta por
        Id > últimoIdConocido y muestra notificación sin recargar.
